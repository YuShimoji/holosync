# Operator Workflow

人間オペレーターの実ワークフロー・痛点・品質目標を保持する正本。

## 全体フロー
- 実装 (assistant) → lint / E2E 自動検証 (assistant) → バッチ単位で再ビルド (assistant) → user が `dist/HoloSync-win32-x64/HoloSync.exe` で手動確認 → フィードバック → 修正

## 工程ごとの痛点
- **Electron パッケージ版はビルドしないと反映されない**: `npm start` (開発) はライブ反映されるが、配布用 `.exe` はビルドスナップショット。ユーザーは通常 `.exe` で最終確認するため、再ビルドを忘れると「修正したのに反映されない」と感じる。
- `npm run build` は electron-packager が Electron 本体を GitHub Releases から取得するため 1-2 分かかる。軽微な修正ごとに毎回走らせると時間コストが大きい。

## 品質目標
- user が `.exe` でテストしたいタイミングに、常に最新の修正が反映されている
- assistant は「いま再ビルドすべきタイミング」をこのポリシーに基づいて判断する

## Actor Boundaries
- 実装・自動検証 (lint / E2E): assistant
- `npm run build` 実行: assistant (user が明示的に止めない限り、下記タイミングで自動実行)
- `.exe` での実機確認: user (感性判断・実動作確認)
- 不具合の報告と次方針決定: user

## 手動工程 / 自動化禁止工程
- 視覚的な違和感の判定
- 実機での操作フィーリング確認
- UX 改善優先度の判断

## 運用ルール
- 一度説明された workflow pain はここへ固定する
- 「本制作へ進む前に workflow proof が必要」な案件では、その proof 条件もここへ残す

## Build Checkpoint Policy (2026-04-15 確立)

Electron パッケージ版の再ビルドは以下のタイミングで走らせる。個別コミットごとの毎回ビルドは禁止。

### 自動再ビルドすべきタイミング

| タイミング | 条件 |
|---|---|
| **スライス完了時** | SP-XXX / F-YY のような仕様上の 1単位が done になった時 |
| **UX 修正バッチ完了時** | user 報告の UX バグ/摩擦を複数件まとめて修正した時 |
| **セッション終了手前** | handoff 前で user が実機確認したいタイミング |
| **ユーザー明示要求時** | 「ビルドして」「確認したい」等 |

### 再ビルドしなくてよいタイミング

| タイミング | 理由 |
|---|---|
| docs/\*.md のみの変更 | 実行コードに影響しない |
| コメント修正・typo | 挙動に影響しない |
| 単一ファイルの内部リファクタ | 他の変更とまとめる |
| lint/format 自動修正のみ | 挙動に影響しない |
| テスト (e2e/) の修正のみ | パッケージに含まれない (ignored) |

### 意思決定手順

assistant は修正完了時に以下を順に確認する:

1. 変更内容は実行コードに影響するか? (No なら build 不要)
2. 直近の最終ビルドから実行コード変更コミットが 3件以上蓄積しているか? (Yes なら build 候補)
3. UX/挙動/見た目に関わる user-visible な変更を含むか? (Yes なら build 候補)
4. build 候補であれば、次の user 返答を待たずにバックグラウンドで `npm run build` を開始
5. build 完了を user に報告し、`.exe` パスを明示

### ビルド実行中の並行作業

- ビルドは `run_in_background: true` で実行し、出力は随時 Read で確認
- ビルド完了を待つ間、assistant はドキュメント同期・コミットメッセージ整理・次タスクの設計などを進める
- ビルド失敗時は即座に user に報告し、修正/再試行を判断
